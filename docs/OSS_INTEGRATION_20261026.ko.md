# 오픈소스 조합 1차 적용 · 2026-10-26

이번 범위는 **사진 한 장 → 카메라·깊이 증거**와 **실루엣 기반 IR 수치 피팅 코어**다. 필요한 코드만 옮겨 왔다. npm 의존성과 lockfile은 바꾸지 않았다. 엔진 기본 경로에 3D 생성 모델을 추가하지 않았다. 지각(perception) 모델 출력은 기존 깊이 워커 가드와 마찬가지로 `estimated` 증거로만 기록하고 AssemblyIR을 수정하지 않는다. 피팅 결과는 `inferred` 제안이며 원본 IR을 변경하지 않는다. 전체 `quality:production` 실패 상태는 그대로이고 이번 변경으로 전체 엔진 완료를 주장하지 않는다.

조사 근거와 라이선스 확인은 `~/Documents/Sceliph_OSS_Integration_Research_20261026/report.md`에 있다.

## 실측 결과

### MoGe-2 vits (ONNX, CPU, Apple M5, 640px, 2400 tokens)
- 추론 약 1.3초, 세션 로드 약 0.2초. host 한정 수치이며 SLA가 아니다.
- 실제 제품 사진(`public/local-references/product-photo-fan-main.jpg`): 흰 배경은 mask에서 빠졌고, 스탠드 다리의 원근 차이와 팬 면의 기울기가 깊이 차이로 나타났다. 추정 FOV는 38.1°, 학습 사전값 기준 중앙 깊이는 2.59m다. 실제 촬영 거리를 모르므로 정확도 판정은 하지 않는다(`benchmarks/oss-integration-20261026/moge-fan/`).

### 정답을 아는 합성 장면 3개 (`benchmarks/oss-integration-20261026/moge-ground-truth/verification.json`)

| 장면 | 실제 FOV | 추정 FOV | 사전값만 쓴 260mm | anchor 적용 후 110mm 검증 치수 | FOV를 알려준 경우 |
|---|---|---|---|---|---|
| a | 40° | 50.7° | 1075mm (+313%) | 119.4mm (+8.5%) | 117.0mm (+6.3%) |
| b | 60° | 50.0° | 1163mm (+347%) | 116.4mm (+5.8%) | 118.6mm (+7.8%) |
| c | 30° | 44.4° | 1018mm (+291%) | 115.8mm (+5.2%) | 113.7mm (+3.4%) |

해석:
- 학습된 metric scale은 mm 증거로 쓸 수 없다. 이번 장면에서는 약 4배 틀렸다.
- 기준 치수 1개를 주면 독립 치수 오차가 +5~9%로 줄어든다.
- FOV를 알려줘도 세 사례에서 일관된 개선은 없었다.
- 이 장면들은 텍스처 없는 합성 CG라 실제 사진의 난이도를 대표하지 않는다. 이 숫자로 합격 기준을 만들지 않았다.
- EEVEE 렌더 바이트는 실행마다 달라진다. 정답 좌표는 재실행에서 일치했고, 각 증거는 저장된 이미지 SHA에 묶여 있다.

### 실루엣 피팅 (`tests/silhouette-parameter-fit.test.ts`)
- 몸체(roundedBox)와 기둥(cylinder) 6개 파라미터를 160px 두 시점 실루엣에 맞췄다. 몸체 가로·세로는 3% 이내로 복원됐고 두 시점 IoU는 0.97을 넘었다.
- **식별 불가 문제를 재현했다.** 첫 구현은 IoU 1.0(픽셀 완전 일치)이면서 기둥 깊이를 46.7mm(정답 30mm)로 반환했다. 기둥 아랫부분이 몸체에 가려지기 때문이다. 그래서 3회 지터 재시작 중 동등하게 좋은 해들 사이의 값 차이가 범위의 2%를 넘으면 `identified: false`로 보고하게 했다. 보이는 윗면 높이는 1mm 이내로 복원되고, 깊이와 위치는 미식별로 표시된다.
- 같은 seed에서 영수증이 완전히 일치한다. 이 테스트는 약 1.9초가 걸린다(직렬 실행 기준).

## 하지 않은 것과 다음 단계
- 실제 사진 → 카메라 자세 + 형상 동시 피팅은 아직 없다. MoGe는 내부 파라미터와 상대 깊이를 주지만, 물체 대비 카메라 외부 자세를 풀어야 실루엣 피팅에 연결할 수 있다. 다음 단계는 기준 치수 + MoGe 포인트맵으로 자세를 초기화하고, 강한 prior를 둔 공동 최적화다.
- 물체 마스크는 아직 MoGe의 유효 영역 mask(배경 제외)만 쓴다. 부품별 마스크는 SAM 2.1 + Grounding DINO 통합이 필요하다.
- Manifold CSG, replicad BREP, Anny 인체 템플릿, Marigold-IID는 다음 묶음이다.
- 지각 출력을 IR에 직접 기록하는 것, 비교용 3D 생성기 실행, 자가수정 횟수 상향은 사용자 결정 사항으로 남긴다.

# 2차 적용: 사진 한 장 → 카메라 자세 + 형상 공동 피팅, SAM 2.1 부품 마스크 · 2026-10-26

이번 범위는 1차에서 만든 부품을 실제 사진 경로로 연결하는 것이다.
- 사진 → MoGe 포인트맵 → 기준 치수 보정 → 카메라 초기 자세
- Grounding DINO + SAM 2.1 부품 마스크
- 카메라·형상 공동 피팅

결과는 `inferred` 제안 파일(`fitted-ir.json`)로만 나오며 입력 IR은 수정하지 않는다. 지각 모델 출력은 여전히 `estimated` 증거이고 IR에 직접 기록하지 않는다. npm 의존성과 lockfile은 바꾸지 않았다.

## 정답 장면 검증 (`benchmarks/oss-integration-20261026/photo-fit-ground-truth/`)

조건: Blender 장면 3개(640×480)를 사용했다.
- 상자 300×150×200mm에 원기둥 r40×180mm
- 시작 IR은 상자 가로 300mm만 맞고 나머지 치수는 틀린 값
- 시점 힌트는 정답에서 방위각과 고도각을 각각 약 15°, 10° 어긋나게 줌
- 기준 치수는 상자 앞면의 260mm
- 카메라 오차는 기준 상자 중심에 대한 상대값이다. 물체 배치와 카메라는 함께 평행이동해도 사진이 같기 때문이다.

### SAM 2.1 분할
- 물체 전체: Blender 알파 마스크 대비 IoU 0.974 / 0.987 / 0.983
- 부품: 0.975~0.993
- 엔진 카메라 변환 자체의 검증으로, 정답 IR을 정답 카메라로 래스터한 결과가 알파 마스크와 IoU 0.996~0.997로 일치했다.

해석:
- **화각을 알면 카메라 위치 오차가 130~190mm에서 6~25mm로 줄어든다.** MoGe 화각 오차(±10~15°)가 초점-거리 결합을 통해 위치 오차로 번진다.
- **기둥 깊이는 두 조건 모두 정답과 무관하다.** 원기둥 윗부분이 이미지 위쪽 경계에서 잘리기 때문이며(`b/fit-known-fov/overlay.png`), 경계 도달 경고로 표시된다.
- **장면 c**는 망원(30°)·낮은 고도라 고도각-깊이 모호성이 크다.
  - 추정 FOV 조건에서는 경고 없이 상자 깊이가 +57% 틀렸다. 재시작 일치는 필요조건일 뿐 충분조건이 아니다. 같은 오답 분지로 모이거나 모델 오차(잘못된 화각) 아래의 진짜 최적해일 수 있다.
  - `lowConfidenceReasons`가 비어 있다고 정확하다는 뜻은 아니다.
- **개발 중 관찰(증거 파일로는 보관하지 않음)**: 깊이 손실이 없던 실루엣 전용 버전에서는 b의 상자 깊이 +35%와 기둥 깊이 +67%, c의 방위각 오차 44°가 나왔고, 경고는 모두 `identified: true`였다. 그래서 깊이 형태 손실과 경계 도달 감지를 추가했다.

# 4차 적용: LLM→AssemblyIR 실행 피드백 루프 · 2026-10-26

`src/engine/assembly-feedback.ts`는 IterCAD·CADENA류 연구에서 효과가 보고된 "컴파일 → 측정 → 구조화 피드백 → 최고점 채택"을 의존성 없이 구현한다.
- **입력**: LLM 원문 텍스트(코드 펜스 1개 허용)와 사용자/증거가 제공한 `sceliph.assembly-requirements/0.1`(필수 부품, 기존 `DimensionContract` 치수, 삼각형 예산). 요구사항을 후보 자신에게서 추출하지 않는다.
- **단계**: parse → schema(기존 `validateAssemblyIR`) → compile(`compileAssemblyIR`) → requirements(기존 `auditDimensionContracts`와 토폴로지). 단계와 통과율로 점수를 매긴다(0~1, 순위용).
- **정확한 수정 지시**: 단순 primitive(회전 없음)의 크기 불일치는 정확한 파라미터 편집으로 돌려준다. 예: `set components[0] (body).geometry.size[1] to 150`, 원기둥 depth와 radius, 구 radius. 그 밖의 형상은 축별 배율로 안내한다.
- **`runAssemblyCorrectionLoop`**: 모델 비의존이다(생성 함수만 주입). 첫 통과에서 멈추고, 마지막 결과가 아니라 **최고점 후보**를 반환한다. 1~6회로 제한한다.
- **기존 계약**: 도메인 선언용 `maximumAttempts: 1` 계약과 기존 경로는 바꾸지 않았다. 이 루프는 별도 모듈이며 UI나 기존 import 경로에 연결하지 않았다.
- **테스트**(`tests/assembly-feedback.test.ts`): 산문 응답 거부, 펜스 JSON 허용, 스키마 단계, 세 치수 불일치의 정확한 수정 문구, 수정을 따른 2회차 통과, 2회차가 나빠지면 1회차 유지.
- **미실행**: 실제 LLM으로 첫 시도와 수정 후 성공률을 측정하지 않았다. 외부 모델 호출은 사용자 승인이 필요하다.

그래서 저장소 파일이나 CLAUDE.md가 프롬프트에 섞이지 않는다. 과제와 가이드는 모델 호출 전에 파일로 고정했다(`tasks.json`, `tasks-v2.json`). 모든 후보와 피드백을 보관한다.

| 실행 | 모델 | 첫 시도 | 피드백 후 | 비용(USD) |
|---|---|---|---|---|
| v1 (명시 치수, 단순 primitive) | claude-haiku-5-5 | 6/6 | 6/6 | 0.005 |
| v2 (회전·삼각함수·배치 계산), 배율 피드백 | claude-haiku-5-5 | 5/6 | 6/6* | 0.011 |
| 같음 | claude-sonnet-5-5 | 5/6 | 6/6* | 0.163 |
| v2, 테셀레이션 진단 피드백 | claude-haiku-5-5 | 5/6 | **6/6** | 0.010 |
| 같음 | claude-sonnet-5-5 | 5/6 | **6/6** | 0.143 |

해석:
- **v1은 천장 효과로 피드백 루프를 평가할 수 없었다.** 그래서 v2를 따로 고정했다.
- **v2에서 두 모델이 첫 시도에 실패한 과제는 모두 `pipe` 하나다.** 모델의 기하는 맞았다(반지름 25mm, 올바른 끝점). 실패 원인은 튜브 기본 `radialSegments = 10`이라 다각형 폭이 47.55mm로 측정된 것이다. 가이드에도 이 옵션이 없었다.
- **\* 거짓 성공**: 첫 피드백은 "축 방향으로 1.051배 키워라"라는 일반 배율 지시였다. 두 모델 모두 반지름을 26.275mm로 부풀려 측정만 통과했다. 실제 형상은 틀어졌으므로 이 6/6은 성공으로 세지 않는다.
- **수정**: 곡면 primitive(튜브·원기둥·구)의 선언 지름이 요구값과 이미 맞는데 측정만 작으면, 반지름은 유지하고 분할 수(4의 배수, 32 이상)를 늘리라고 안내하게 했다. 재실행에서 두 모델 모두 반지름 25를 유지하고 `radialSegments: 32`로 통과했다.
- **이전 실패와 비교할 때 주의할 점**: 이전에 기록된 2/6 실패는 로컬 Qwen3 0.6B의 도메인 선언 과제였다. 모델과 과제가 모두 달라 직접 비교할 수 없다. 이번 과제는 치수가 명시된 텍스트 요청이며, 사진 기반 요청이나 모호한 요청의 성공률을 대표하지 않는다. 과제당 1회 실행이다.

## Manifold `booleanCSG`
- **vendor 방식**: npm 패키지는 CLI/CAD 도구용 전이 의존성 11개를 함께 끌어온다. 그래서 런타임 `manifold.js`, `manifold.wasm`, 타입, LICENSE만 `vendor/manifold-3d-3.5.4/`에 복사하고 SHA를 NOTICE에 기록했다. package.json과 lockfile은 바꾸지 않았다.
- **AssemblyIR 0.1에 하위 호환 연산 추가**:
  - 형식: `{ op: 'booleanCSG', operation: 'union'|'difference'|'intersection', operands: [{ geometry, position?, rotation?, scale? }] }`
  - 피연산자는 primitive와 프로필 연산만 허용한다. 개수는 2~8개, 중첩 깊이는 2까지다.
  - 기존 IR과 기존 바이트는 바뀌지 않는다.
- **검증 리팩터링**: 컴포넌트 형상 검증 스위치를 재귀 함수 `validateGeometry`로 꺼내 피연산자에도 같은 규칙을 적용한다. 오류 문구에 `component.operands[i]` 경로가 들어간다. 스키마에는 `$defs/booleanCSG`를 추가했다.
- **런타임 로딩**: WASM은 비동기 지연 로드한다(`initManifold`, `prepareAssemblyRuntime`). CLI 작업 경로(`morphloom-job`), UI의 AssemblyIR 불러오기, LLM 피드백 루프에서 필요할 때만 불러온다. 불러오기 전에 컴파일하면 명확한 오류로 거부한다.
- **테스트**:
  - 구멍 두 개 판의 부피가 해석값과 일치하고 genus가 2다.
  - 같은 입력에서 바이트가 결정적이다.
  - 엔진 토폴로지 검사(경계 엣지 0)를 통과한다.
  - 합집합·교집합(중첩 포함) 바운딩 박스와 부피가 맞는다.
  - 깊이, 개수, 연산, 피연산자 종류, 0 스케일, 빈 결과를 거부한다.
  - 표준 작업 경로로 GLB를 내보내면 Khronos 검증과 독립 판독을 통과하고 결과가 결정적이다.
- **빌드**: Manifold는 별도 청크(JS 44KB, WASM 541KB)로 분리된다. main 번들은 804.89kB에서 807.68kB가 됐다. Vite가 Manifold의 Node 전용 분기 때문에 `node:module` 외부화 경고를 낸다.

# 6차: 사진 → LLM IR → 사진 피팅 (Blender 정답 대비)

## 무엇을 쟀나
- **정답 장면 5개**: 상자+기둥, 사이드 테이블(다리 4), 머그(테이퍼 몸통+토러스 손잡이), 스탠드(받침·기둥·원뿔 갓), 책장(옆판 2·선반 4·뒤판).

  - 좌표계 확인: 정답 IR을 정답 카메라로 래스터화하면 Blender 알파와의 IoU가 0.9994~0.9999다.
- **모델 입력**: 사진, 알려진 치수 1개, 수평 화각, 부품 id와 설명.
- **모델 출력**: `{view: {azimuthDeg, elevationDeg}, assembly}`.
- **피드백**: 라운드 사이에는 구조 문제(파싱·스키마·컴파일·누락 부품)만 알려 주고, 정답은 절대 보여 주지 않는다.
- **피팅**: 모델 IR에서 그대로 시작한다. 마스크는 Blender 부품 마스크(oracle)를 쓴다. SAM 오차를 빼고 피터만 보기 위해서다. 화각은 알려진 값을 쓴다.
- **채점** `compareAssemblyToTruth`:
  - 부품 크기 오차는 정답 크기에 대한 비율이다.
  - 기준 부품 대비 위치와 바닥 높이 오차는 전체 크기에 대한 비율이다.
  - 사진 한 장으로는 정할 수 없는 90° 회전과, 같은 부품끼리의 순서 바뀜은 가장 잘 맞는 경우로 채점한다.
- **규약**: `benchmarks/oss-integration-20261026/photo-llm/protocol.json`(sha256 `6c6d1983…`)을 실행 전에 고정했다. 장면당 1회 실행이다.

## 엔진 변경
- `derivePhotoFitParameters`: 모델 IR에서 피팅 파라미터를 자동으로 만든다.
  - 알려진 치수와 같은 기준 부품의 수치는 고정한다.
  - 형상이 같은 부품은 한 그룹으로 묶는다. 크기는 공유하고, 위치는 크기가 같은 시작값끼리 비율로 연동한다(거울 대칭 다리는 −1).
  - 곧은 원기둥은 곧게 유지한다.
  - 기준 부품과 똑같은 복사본도 기준의 크기(고정된 치수 포함)를 공유한다.
- `SilhouetteFitParameter.links`: 파라미터 하나로 여러 슬롯을 움직인다. 시작값이 `value × ratio`와 다르면 거부한다.
- 카메라만 맞추는 피팅도 허용한다(형상 파라미터 0개).
- `fitPhotoShape` 변경 3가지:
  - **물체 주변 crop**: 마스크 박스에 15% 여백을 둔 영역만 래스터화한다. receipt의 카메라는 원본 이미지 픽셀 좌표로 되돌려 기록한다.
  - **2단계 피팅**: 카메라만 먼저(평가 예산 1/3) 맞추고, 그다음 카메라와 형상을 같이 맞춘다. 2단계 보폭은 0.08이다.
  - **재시작 간격 고정(0.2)**: 이 간격을 보폭에 묶으면 재시작이 늘 같은 답을 내 '식별됨' 판정이 무의미해진다. 그래서 고정했다.
- 점검 실행에서 찾아 고친 문제 3가지:
  - 실루엣 경계에 놓인 앵커는 MoGe 유효 깊이가 없다. 앵커를 면 안쪽으로 옮겼다.
  - 작은 물체는 160px 래스터에서 약 48px밖에 안 됐다. crop으로 해결했다.
  - 동시 최적화가 나쁜 초기 카메라를 형상으로 보상했다. 2단계 피팅으로 해결했다.
- MoGe의 미터 단위 스케일은 무늬 없는 CG에서 모든 장면을 약 3.5m로 추정했다. 앵커 보정 뒤 깊이는 정답과 일치했다(상자+기둥: 0.77m 대 0.77m). 앵커가 필요한 이유를 다시 확인한 셈이다.

- **비용**: Haiku $0.0064, Sonnet $0.064.
- **피팅이 확실히 도운 경우**: 모델 IR이 10% 이상 틀린 6건 중 5건이 1~7%로 줄었다. Haiku 테이블은 중앙값은 줄었지만 실루엣 IoU가 0.63에 그쳤고, 경고 18개를 냈다.
- **피팅이 해친 경우**: 모델 IR이 이미 정확할 때 악화됐다(Haiku 상자 0%·책장 0%, Sonnet 책장 3.3%). 모델이 흔한 규격 치수(두께 20, 깊이 300 등)를 그대로 맞힌 장면에서, 피팅이 오히려 노이즈를 더했다.
- **결론**: 지금 상태의 피팅은 무조건 적용하면 안 되는 제안이다. 모델 IR과 피팅 결과 중 무엇을 받을지 정하는 수락 기준이 필요하다. 수락 기준은 이번 결과를 보고 사후에 정하지 말고, 다음 실행 전에 미리 고정해야 한다.
- **최대 오차는 여전히 크다**: 가려진 뒤판, 손잡이 굵기 등에서 25~250%다. 가려진 치수는 사진으로 정해지지 않는다.

## 한계
- 무늬 없는 합성 CG, 화각을 알고, 마스크도 정답(oracle)이다. 실제 사진은 이보다 어렵다.

# 7차: 피팅 수락 기준 사전 등록과 검증 (2026-10-27)

목표는 6차의 문제, 곧 "이미 맞는 IR을 피팅이 망친다"를 정답 없이 사진 정보만으로 막는 것이다. 순서는 다음과 같다.
1. 6차 응답 10건을 개발용으로만 써서 원인을 찾고 기준값을 정했다.
2. 기준을 `protocol-v2.json`(sha256 `1b8c2472…`)에 고정했다.
3. 새 응답 20건(2회 × 5장면 × Haiku/Sonnet)으로 검증했다.

## 원인 진단 (개발용 데이터)
- **정답 형상을 넣으면 피팅은 아무것도 바꾸지 않는다.** 1단계(카메라만) IoU 0.985~0.997, 2단계 변경 0. 피팅 자체가 형상을 흔드는 것이 아니라는 뜻이다. LLM IR에 남은 다른 오차를 맞추려다 형상이 끌려간다.
- **망친 값의 대부분은 사진 한 장으로 보이지 않는 값이었다.**
  - 정중앙·같은 축 위에 있어야 할 위치의 좌우·앞뒤(스탠드 기둥 x/z, 손잡이 z)
  - 가려진 치수(뒤판 두께, 옆판 두께, 거의 옆에서 본 상판 두께)
- **사이드 테이블의 실패 원인**: LLM이 다리 번호를 정답과 다르게 붙였다(leg-1을 반대편에). 번호별 부품 마스크가 다리를 반대편으로 끌었다. 실제 SAM 마스크에서도 생기는 문제다. 똑같이 생긴 부품의 번호는 사진으로 정할 수 없기 때문이다.

## 엔진 변경
- **`derivePhotoFitParameters` 정렬 고정(`lockAligned`, 기본 켬)**: 위치 축이 기준 부품 좌표나 전체 물체의 중심선 위에 정확히 있으면 구조적 주장(같은 축, 대칭면)으로 보고 피팅하지 않는다. 결과의 `aligned`에 기록한다.
- **`fitAssemblySilhouette` 민감도 게이트(`sensitivityGate`)**:
  - 최적화 전에 각 형상 변수를 범위의 ±5%만큼 움직여 본다.
  - 손실 변화(절댓값의 큰 쪽)가 기준 미만이면 그 변수를 고정한다(`frozen`, `identified: false`).
  - 개발용 데이터에서 0.002 미만인 변수 8개 중 6개가 피팅으로 악화됐다. 다음으로 작은 값은 0.0042라 경계가 뚜렷했다.
- **`mergeGroupPartMasks`**: 똑같은 부품 그룹의 마스크를 하나로 합쳐 번호와 무관하게 맞춘다. Haiku 테이블의 카메라 단계 손실이 0.57에서 0.045로 줄었다.
- **`fitPhotoShape`**: 1단계 결과를 `cameraOnly`로 돌려준다(LLM 형상 그대로 카메라만 맞춘 손실과 IoU).
- **`decidePhotoFitAcceptance`**: 정답 없이 피팅 결과 수락 여부를 정한다. 다음 셋을 모두 만족해야 수락한다.
  - 카메라만 맞춘 손실 대비 30% 이상 감소
  - 자유 변수 하나당 5% 이상 감소(정보량 기준)
  - 피팅 후 IoU 0.9 이상
- **평가 스크립트**: 위 설정은 프로토콜에 있을 때만 켠다. v1 프로토콜은 이전과 똑같이 재현된다. `final`(수락 시 피팅 결과, 거부 시 LLM IR)도 채점한다.

## 개발용 데이터 결과 (기준값을 이 데이터로 정했으므로 낙관적)
- 크기 오차 중앙값: LLM 9.8% → 최종 2.0%
- 최댓값: 20% → 5%
- 책장 2건은 거부됐다(자유 변수당 감소 2~3%). 나머지 8건은 수락됐다.

## 사전 등록 검증 결과 (새 응답 20건, `test-v2-summary.json`)

| 지표 | LLM IR | 항상 피팅 | 수락 기준 적용(최종) |
|---|---|---|---|
| 크기 오차 중앙값 | 8.1% | 5.2% | **5.0%** |
| 장면별 중앙값의 최댓값 | 40% | 10% | 11.4% |
| 위치 오차 중앙값 | 0.67% | — | 0.62% |
| 10% 이내 항목 비율(평균) | 76.4% | — | **88.6%** |

- **기준 1 "중앙값 감소"**: 통과. 8.1%에서 5.0%로 줄었다.
- **기준 2 "2%p 넘게 나빠진 경우 2건 이하"**: **실패**. 5건이 나빠졌다.
  - 상자+기둥 3건: 2.5→5.7, 3.3→5.6, 0→5.2
  - Haiku 책장: 2.0→10.0
  - Sonnet 머그: 4.6→8.7
- **수락 기준이 거의 일을 하지 못했다.** 20건 중 16건을 수락했고, "항상 피팅"과 차이가 0.2%p뿐이다. 거부한 4건 중 2건은 2단계가 개선하지 못해 원래 값으로 되돌아간 경우였다.
- **악화의 형태**: 상자+기둥에서는 상자 높이가 늘고 깊이가 줄었다(150→168, 200→168). 비스듬히 위에서 본 사진 한 장으로는 높이와 깊이가 서로 맞바뀔 수 있다. 기둥 반지름도 약 5% 줄었다. 이 사례들에서는 LLM IR의 위치도 틀려 있었다. 그래서 피팅이 위치를 고치면서 손실이 실제로 크게 줄었고, 수락 기준이 그 차이를 구분하지 못했다.
- **비용**: 20건 $0.154.

## 결론
- **정렬 고정, 민감도 게이트, 마스크 합치기는 효과가 있다.**
  - 피팅의 최댓값을 크게 줄였다. 6차 "항상 피팅"의 최댓값은 11.7%, 이번에는 10%다(LLM은 40%).
  - 10% 이내 비율은 76%에서 89%로 올랐다.
- **"이미 맞는 IR을 해치지 않는다"는 아직 달성하지 못했다.** 사진 한 장 피팅에는 약 5% 오차 바닥이 있다. LLM이 5% 안쪽으로 맞힌 장면에서는 피팅이 오차를 그 바닥까지 끌어올린다.
- 다음 시도는 수락 여부를 한 번에 정하는 방식이 아니라, 형상 변수에 LLM 값을 중심으로 한 사전분포를 주는 방식(MAP)이 맞다. 사진이 강하게 반대할 때만 숫자가 움직이게 하는 것이다. 이번 30건 전체를 개발용으로 쓰고, 새 응답으로 다시 사전 등록 검증해야 한다.

  - 가로·깊이 오차: 중앙값 1.7% → **5.6%**, p75 5.2% → **12.1%**
  - IoU 0.870 → **0.849**, Chamfer 0.0138 → 0.0162
  - B1 대비 IoU +0.20(30건 중 26건 우세). B1의 가로·깊이 오차 중앙값은 21.3%다.
- **해석**: 사진만으로도 형상은 거의 유지된다. 가로·깊이 정확도는 상품명 속 치수 덕분에 약 3배 좋아진 것이다. 리스팅을 쓰는 실무 조건에서는 정당한 입력이지만, "사진만으로"라고 주장하려면 5.6% / 12.1%를 인용해야 한다.

## 결론
- **실제 카탈로그 사진에서 LLM이 쓴 IR이 처음으로 정답 기반으로 측정됐다.** 하드서피스 제품 30건에서 다음을 보였다.
  - 새 시점 실루엣 IoU 중앙값 0.87
  - F-score@5% 0.99
  - Chamfer 대각선의 1.4%
  - 가로·깊이 오차 1.7%(사진만으로는 5.6%)
  - 단순 기준선을 큰 차이로 이겼다.
- **사진 한 장 실루엣 피팅은 실사진에서 새 시점 형상을 나쁘게 만든다**(항상 피팅 0.738 대 0.870). 수락 게이트가 대부분을 막았지만 수락한 5건 중 일부도 손해였다. 실사진에서는 피팅을 기본으로 끄고 진단용으로만 쓰는 것이 맞다. 합성 CG에서 본 개선(7차)은 실사진으로 옮겨 가지 않았다.
- 7차의 "약 5% 오차 바닥" 문제는 실사진에서 크기 정확도의 병목이 아니다. 병목은 형상 어휘(가는 구조, 날개)와 사진 한 장의 정보량이다.

# 9차: 지표 재점검(9a)과 사진 2장 입력 사전 등록 검증(9b) (ABO, 2026-10-27)

## 계획과 반대 검토
- 원래 다음 후보는 "가는 구조 어휘"였다. 초안(`abo-photo/plan-review-9/plan-draft.md`)은 하위 항목의 낮은 IoU를 지표 민감도 탓으로 진단하고, 사진 2장 입력을 제안했다.
- Opus 반대 검토 판정은 "수정 후 승인"이다(`abo-photo/plan-review-9/reviews.md`). 주요 지적은 세 가지다.
  - 입력 프레임 0은 대부분 3/4 시점이라, "깊이를 못 본다"는 말은 램프·조명·선풍기에만 맞는다.
  - 초안이 인용한 수치는 상품명에 치수가 남은 조건에서 나온 것이었다.
  - 지표 민감도 진단은 하위 6건 중 절반에만 맞는다.
- 반영
  - 지표를 먼저 점검했다(9a).
  - 제품 유형으로 층을 미리 나눴다(thin = LAMP·LIGHT_FIXTURE·ELECTRIC_FAN).
  - 오차는 항목 단위와 yaw 무관 지표로 바꿨다.
  - 팔마다 3회 반복했다.
  - 프레임 간격 5°를 확인했다.
- B2 재정의 요구는 받아들이지 않았다. 90° 떨어진 두 실루엣의 헐은 절대 방위가 달라도 같은 모양이 회전할 뿐이고, 채점이 yaw를 탐색한다.

## 9a: 지표 재점검 (새 LLM 호출 없음)
- `compareMeshShapes`에 `footprintMm`과 `footprintError`를 더했다. 각 메시 자체의 x/z 최소 면적 사각형에서 잰 [긴 변, 짧은 변]이라 yaw 정렬과 무관하다.
- `scripts/abo-rescore.ts`로 8차 실행 3개를 320px 래스터로 다시 채점했다(`abo-photo/*/rescore-r320.json`). SAM은 결정적이며 replay로 b0/b1/llm 점수가 완전히 같음을 확인했다.
- 래스터 160→320에서 IoU는 거의 변하지 않았다. 전체 LLM은 0.870→0.880, thin은 0.522→0.514다. **"가는 구조의 낮은 IoU는 래스터 해상도 탓"이라는 가설은 기각했다.** thin의 F@2%는 0.63, 가구는 0.85이고, 실제 형상 오류다.
- **8차 크기 오차 정정.** 8차는 항목마다 x와 z를 합쳐 n=60으로 계산했고, yaw 정렬 뒤 AABB를 쓰므로 회전과 크기가 섞였다. 항목별 최대 footprint 오차로 다시 재면 다음과 같다.

| 8차 실행 | 이전 보고 (중앙값 / p75) | footprint 오차 (중앙값 / p75) |
|---|---|---|
| test-sonnet (상품명 치수 있음) | 1.7% / 5.2% | 4.4% / 11.1% |
| explore-strip (사진만) | 5.6% / 12.1% | 9.1% / 19.3% |

- 8차의 결론은 그대로다. LLM IR은 기준선을 이긴다(320px IoU 28/30, Chamfer 29/30). 피팅은 IoU 기준 12/30에서 해롭다.

## 9b: 사진 1장 대 2장
- 데이터: `abo-multiview/selection.json`. 같은 시드 순서를 8차 55건 뒤에서 이어 뽑았고, 메시 시그니처가 겹치는 6건을 제외했다. 이름과 메시 메타데이터만으로 변형 제품 4건을 찾아 같은 층 예비 항목으로 바꿨다. test는 thin 24건과 other 12건이다.
- 팔(arm): 상품명 치수는 제거하고 리스팅 높이를 주며, 피팅은 쓰지 않는다.
  - a1: 프레임 0
  - a2: 프레임 0과 18(같은 카메라, 90°)
  - b0: 상자
  - b1: 정면 돌출
  - b2: 두 실루엣 시각 헐(`visualHull`)
- 가이드는 8차 test 가이드 그대로다. a2 요청에만 두 번째 사진을 설명하는 한 줄을 더했다.
- dev(8차 dev 10건, 1회)는 프롬프트가 동작하는지만 확인했다. a2 footprint는 3건 나아지고 6건 나빠졌고, 대부분 3/4 시점 가구였다. 그래서 "footprint-gain 실패"를 예측해 사전 등록에 적었다.
- 사전 등록: `protocol-test.json`(sha256 `69b07de5…`)과 `preregistration-hashes.txt`. Sonnet으로 3회 반복했다. see-through 3건은 사전 규칙대로 제외해 n=33이다(thin 21, other 12). 비용은 5.23달러다.

| thin 21건 (3회 평균의 중앙값) | b1 | b2 헐 | a1 | a2 |
|---|---|---|---|---|
| footprint 오차 | 12.3% | 7.3% | 10.3% | **5.2%** |
| footprint p75 | 35.9% | 35.5% | 21.7% | **12.9%** |
| Chamfer/diag | 0.041 | 0.029 | 0.020 | **0.015** |
| F@2% | 0.35 | 0.51 | 0.67 | **0.78** |
| IoU (320px) | 0.59 | 0.62 | 0.73 | **0.79** |

- 짝지은 차이 a2−a1(thin)
  - footprint −2.6%p, CI [−6.0, −0.9], 18건 나아짐 / 3건 나빠짐
  - IoU +0.035, CI [0.002, 0.077]
  - F@2% +0.044
- 가구 12건(other): a2−a1 footprint +0.6%p, CI [−1.3, 3.0], IoU −0.011. 효과가 없다. 3/4 시점 한 장에 이미 깊이가 보이기 때문이다. 이 층은 사전 등록에서 기준 없이 보고만 하기로 했다.
- **기준 4/4 통과**
  - footprint-gain: thin, 중앙값 < 0이고 CI 상한 < 0
  - no-shape-loss: Chamfer 차이 −0.0019 ≤ +0.001
  - beats-hull: 전체 a2−b2 Chamfer −0.017, CI [−0.022, −0.012], 31/33 나아짐

- 주목할 점: thin 층의 footprint만 보면 LLM 없는 2장 헐(7.3%)이 LLM 1장(10.3%)보다 낫다. 형상 지표(Chamfer, F, IoU)에서는 a1이 헐보다 낫다.

## 결론
- 두 번째 사진은 정면 촬영이 많은 가는 구조 제품(조명·램프·선풍기)에서 크기와 형상을 함께 개선한다. 이미 3/4 시점인 가구에서는 효과가 없다.
- 운영 규칙으로는 이렇게 정리한다. 정면 사진 한 장뿐이고 깊이가 보이지 않으면 직교 측면 사진을 한 장 더 요청할 가치가 있다. evidence-pack의 "깊이 미해결" 신호와 연결할 후보다.
- 2장 입력 뒤 thin 층의 F@2%(0.78)는 가구(0.75)와 비슷해졌지만, IoU는 0.79 대 0.88로 여전히 낮다. 가는 막대와 날개의 위치·각도 오차가 남아 있어 형상 표현 개선 후보는 남는다.

## 한계
- 직교 90° 측면 사진은 실제 사용자 입력보다 이상적이다. 이번 결과는 "두 번째 시점의 상한에 가까운 값"이다.
- 시각 헐 기준선은 정사영과 수평 시점을 가정한다. 실제 고도 약 15°와 원근은 반영하지 않았다.

- 실행 중 제외(see-through)에 대한 예비 교체 규칙을 사전 등록에 적지 않았다. 그래서 교체하지 않았고 n이 줄었다.
- 텍스처와 겉보기 지표는 여전히 없다. 전용 생성기와의 비교도 없다.
